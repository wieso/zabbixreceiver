## Замечания

### 1. P1 — используемый toolchain имеет известные уязвимости

Места: `go.mod:3`, `receiver/zabbixreceiver/go.mod:3`, `Dockerfile:1`, `.github/workflows/ci.yml`, `.github/workflows/release.yml`.

На установленном `go1.26.5 darwin/arm64` govulncheck v1.8.0 сообщает о достижимых уязвимых символах: 7 уязвимостей стандартной библиотеки для Collector, 5 для отдельного receiver. Общие: GO-2026-6218, GO-2026-6090, GO-2026-6089, GO-2026-5972, GO-2026-5026; у сборки дополнительно GO-2026-6091 и GO-2026-6088. Для всех сканер указывает исправление в Go 1.26.6.

Примеры официальных записей: [net/url](https://pkg.go.dev/vuln/GO-2026-6218), [crypto/tls](https://pkg.go.dev/vuln/GO-2026-6090), [net/http](https://pkg.go.dev/vuln/GO-2026-6089). Статическая достижимость не доказывает эксплуатацию в конкретной конфигурации: например, запись net/http относится к включённому unencrypted HTTP/2.

**Предложение:** обновить toolchain до исправленной поддерживаемой версии, пересобрать артефакты, повторить сканирование; добавить govulncheck обоих модулей и проверку итоговых бинарников в release gate. `go 1.26.0`, `1.26.x` в CI и плавающий Docker-тег сами по себе не подтверждают версию уже собранного артефакта. Проверка здесь относится к локальному toolchain; версия компилятора опубликованных бинарников не установлена.

### 2. P1 — секрет из URL попадает в журнал при сетевой ошибке

Место: `receiver/zabbixreceiver/internal/zabbix/client.go`, `operationError` / `redactErrorChain`.

Безопасный `safeEndpoint` удаляет query, но вложенная ошибка `http.Client.Do` содержит исходный URL. Redaction скрывает только точное значение API-токена. При URL вида `http://example.invalid/api?access_token=review-query-secret` и отменённом контексте воспроизведена ошибка:

```text
zabbix host.get at http://example.invalid/api: Post "http://example.invalid/api?access_token=review-query-secret": context canceled
```

Это синтетический секрет из теста. Условие дефекта — секрет в query URL, например для промежуточного шлюза; обычный Bearer API-токен данным воспроизведением не раскрывается. Receiver журналирует ошибки задания, поэтому такой query-секрет попадёт в логи. Это нарушает обещание безопасного контекста сетевых ошибок.

**Предложение:** отдельно санитизировать `*url.Error` и вложенные ошибки, сохраняя `errors.Is/As`, либо явно запрещать неподдерживаемые credentials/query в URL. Добавить проверки отмены, timeout, ошибок транспорта и перенаправлений с синтетическими секретами.

### 3. P2 — deflate обходит лимит размера входного тела

Места: `receiver/zabbixreceiver/streaming_compression.go`, ветка `deflate`; `receiver/zabbixreceiver/streaming.go`, чтение decoded body до передачи downstream.

`zlib.NewReader` заканчивает чтение после первого zlib-потока. Остаток закодированного HTTP-тела не проверяется до отправки метрик. Реальный handler в дополнительном тесте принял корректную сжатую запись с дописанным хвостом:

```text
encoded=20080 limit=1024 status=200 batches=1
```

По docs/configuration.md превышение лимита сжатого тела должно давать 413 и ноль переданных пакетов. Ограничение распакованных байтов остаётся; этот тест не доказывает неограниченное выделение памяти.

**Предложение:** проверять весь encoded body и ошибки ограничивающего reader до downstream, учитывая read-ahead декомпрессора. Проверять Content-Length недостаточно: нужны также chunked-запросы. Добавить регрессии с хвостом, повреждением и превышением лимита для всех кодирований.

### 4. P2 — Kubernetes rollout допускает двух владельцев API-шарда

Место: `deployments/kubernetes/deployment.yaml:7`.

При `replicas: 1`, `maxSurge: 1`, `maxUnavailable: 0` старый и новый Pod могут одновременно опрашивать одинаковые items и отправлять одинаковые серии. Приёмник не использует lease/fencing; обычная health-check readiness не проверяет владение шардом. Если перекрытие затянется до запуска values, появятся повторные точки и дополнительная нагрузка на Zabbix. Поведение контроллера соответствует [документации Kubernetes](https://kubernetes.io/docs/concepts/workloads/controllers/deployment/).

Это ограничение честно упомянуто в docs/architecture.md, но поставляемый манифест всё равно создаёт риск при штатном обновлении.

**Предложение:** для простого одиночного API-экземпляра использовать Recreate с документированным перерывом; при требованиях к HA — внешнее управление единственным владельцем с fencing/lease. Отдельный Streaming Deployment может использовать rolling update. Проверка: во время rollout один API-шард опрашивает только один владелец.

### 5. P2 — руководство по масштабированию противоречит реализации

Места: `docs/scaling.md:67`, `docs/scaling.md:96`, `docs/scaling.md:186`.

- Написано, что сжатый HTTP-вход не поддерживается; код поддерживает gzip, zstd, deflate, snappy.
- Описано отклонение всего пакета при ошибке HTTP-пакета без разделения ошибок чтения и некорректных строк. Невалидные JSON/значения теперь пропускаются, остальные записи могут получить 200.
- Написано, что API emitted_points увеличивается до успешного downstream; текущий receiver увеличивает его после успешного ConsumeMetrics.

Актуальное docs/configuration.md описывает эти изменения правильнее. Разночтения влияют на расчёт ресурсов, трактовку потерь и мониторинг.

**Предложение:** синхронизировать руководство с текущим контрактом, отдельно описать память декодеров и семантику HTTP 200 при пропуске строк. Исторические результаты бенчмарков привязать к версии кода: они не доказывают параметры новых метаданных/сжатия.

### 6. P2 — быстрый старт не запускает обещанную Grafana

Место: `Makefile:54`, связанное обещание — README, быстрый старт.

`make demo-up` перечисляет сервисы явно, Grafana среди них нет. Она не является зависимостью выбранных сервисов. На чистом стенде обещанная панель после этих команд недоступна. Наличие ранее вручную запущенной Grafana скрывает проблему.

**Предложение:** включить grafana в demo-up и проверку готовности панели. Дефект подтверждён составом Makefile/Compose; полный чистый старт с удалением существующего стенда не выполнялся.

## Эксплуатационные предложения

Это ограничения/доработки, зависящие от требований эксплуатации, а не скрытые нарушения уже описанного контракта:

1. Определить допустимые потери и задержку. API читает lastvalue и не восстанавливает историю. Streaming HTTP 200 с batch означает приём pipeline, а не запись в VM. При требовании сохранности после crash нужна архитектура устойчивой очереди и явная граница подтверждения. WAL экспортёра полезен, но не делает входной ack транзакционным. См. [OpenTelemetry resiliency](https://opentelemetry.io/docs/collector/resiliency/).
2. Для production-профиля задать проверенные размеры batch/очереди, ограничение конкурентных HTTP-запросов на ingress и сетевой запрет обхода ingress. memory_limiter запускается после построения batch и не ограничивает все выделения handler. Оценить также память zstd-декодеров и метаданных.
3. Если большой API-каталог не укладывается в 8 MiB, разделять видимость отдельными пользователями либо доработать discovery. Локальные regex и items_per_request не устраняют этот предел. Не повышать лимит ответа без оценки пиков памяти.
4. Провести нагрузочные и отказные испытания на целевом профиле: высокая кардинальность, длинные теги, burst, недоступность backend, рестарт Collector, rollout, исчерпание retry и disk-full при WAL. Сверять число исходных/записанных точек, задержку, RSS и очереди. Существующие 30-секундные измерения не являются длительной приёмкой.
5. Подключить оповещения на отсутствие свежих точек/discovery, ошибки и очередь экспорта. Проверка `/` подтверждает состояние процесса, но не сквозную доставку. Задать владельца и процедуру восстановления для API-шардов.
